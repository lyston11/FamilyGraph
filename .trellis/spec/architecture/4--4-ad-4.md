# 4. 连接与空间成员状态机 `[AD-4]`

### Relation FSM
```
pending ──accept──> active        pending ──reject──> rejected(终态)
pending ──cancel──> cancelled(终态, 发起方)
active  ──revoke──> revoked(终态, 任一方; 断连轨 D8)
约束: 同一对用户最多一条非终态边 (partial unique index);
      自环禁止 (CHECK from_user != to_user); elder 边成环检测拒绝
反向显示: 不存反向行; 展示时结构类反译 elder↔younger / peer,spouse 对称,
      称谓标签始终显示创建者视角原文 [D3]
```

### SpaceMember FSM
```
pending ──accept──> active    pending ──reject/withdraw/expiry(30d)──> 终态
active  ──remove──> removed(终态, owner 或本人)
幂等: UNIQUE(space_id, user_id) 仅一行, 重复申请返回既有 pending
```

### 合并请求（回答"一次申请还是两次申请"）
- **connection_request（M1/M2 主流程）**：一份请求同时携带 `relation{dir_class,label}` + 可选 `space_membership(space_id)`。对方一次接受 → 两者同时 active；拒绝 → 同时取消。消除"关系 active 但空间 pending"的中间权限态。
- **新建账号例外（复审澄清）**：由代管人创建 **managed 新档**时，relation 与可选的 space_membership **直接 active**，不走确认流——创建者即代管人，D4 锁定语义本就如此；只有目标为**已存在或已 claimed 的账号**才进入 pending 合并确认流。
- **join_request（M2 家族视图摘要卡）**：仅携带 space_membership，无新关系边。准入与审批（09-20 家族空间限定）：
  - **同族门禁**：申请人必须与 target 同属**该** active `lineage` 空间；仅凭可见性 / `space_profile_refs` / pending 关系不得申请。不同族 → 403 `SPACE_JOIN_NO_RELATION`（不同族只能走邀请码途径）。
  - **空间限定**：目标空间只能是 target 在该 lineage 下 active 的家庭空间（`kind='household' AND lineage_space_id=<该 lineage>`）；不再回退「target 任意 owned household」的跨族解析，显式传入不属于该 lineage 的空间 → 403 `SPACE_FORBIDDEN_ACTOR`；该 lineage 下无可选空间 → 409 `SPACE_JOIN_NO_TARGET_SPACE`。
  - **家庭与家族分离**：加入 `household` **不等于**加入配对 `lineage`；`household` 成员资格不自动获得家族树读取权，也不因 `lineage_space_id` 配对而自动插入 lineage 成员行。读家族树必须另有该 lineage 的 active membership。
  - **家族空间访问申请**：家庭空间 active 成员可对配对 lineage 发起独立 pending（`POST /spaces/lineage-access-requests`）；须是 `household`、已配对 lineage、本人尚非 lineage 成员，且 lineage 存在可审批的 active 成员（默认 owner），否则 409 `SPACE_LINEAGE_ACCESS_UNAVAILABLE`。
  - **目标空间解析**：只取 target 为 owner 的 `household`（按空间 id 稳定取第一个）；不得回退到 target 的任意 active 成员资格，否则会落到申请人自己的空间。target 无管理者空间 → 409 `SPACE_JOIN_NO_TARGET_SPACE`。
  - **审批链（09-20，取代 09-19 的单一判据）**：三条加入路径统一由**该空间 active `space_admin`（房主）**先批准。
    - `invite`（邀请）：房主批准 → **仍需受邀人本人接受** → active；
    - `join_request`（本人申请）/ `code`（邀请码兑换）：提交方即申请人/兑换方，其提交已是同意，**房主批准即 active**；
    - 自批判据是「被批准的人就是批准人自己」（`member.user_id == actor_id`），**不是**「发起人就是批准人」——房主自己建码/发邀请是常见情形，按发起人判定会让邀请码路径死锁；
    - 顺序不可颠倒：`origin` 非 NULL 且未获房主批准时，受邀人 accept 返回 403；
    - 状态持久化在独立表 `space_member_approvals`（`member_id` 主键、`origin`、`owner_approved_at`、`approved_by`）。**无本行 = 历史 pending 行，沿用旧语义**（受邀人本人接受即可），迁移不改既有行为；
    - 邀请码不再「兑换即生效」：此前任何持码者可绕过房主直接成为 lineage 成员并读到家族树。
  - **加入必须填写关系词（09-20）**：三条路径都必填 `relation_label`（自由文本，≤64），记在发起方与对方之间（见文末「成员关系词标注」）。

### 成员邀请与退出（09-20 补充）

- **邀请已有账号（空间内）**：`POST /spaces/{space_id}/members`（`commands.spaces.invite_member`）由该空间 active 成员发起，只产生 pending；受邀人本人接受后才 active。空间治理面板与邀请码路径使用此命令。
- **家族空间内双向加入（个人公示页）**：`GET /spaces/family-space-options?lineage_space_id=&target_user_id=` 只读返回 `shares_lineage` + `invite[]`（我在此 lineage 下的家庭空间 × 目标状态）+ `join[]`（对方在此 lineage 下的家庭空间 × 我的状态）；状态三态 active/pending/none（终态归 none 可再操作）。写路径：邀请用 `POST /spaces/family-invitations`（`commands.spaces.invite_into_family_household`），申请用 `POST /spaces/join-by-user`；两者都要求双方同属该 lineage 且空间属于该 lineage，都只产生 pending（邀请需对方接受，申请需该空间管理员批准，申请人不得自批）。不同族时两个方向都不可用，只能走邀请码。
- **退出空间**：`DELETE /space-memberships/{member_id}`（`commands.spaces.leave_or_remove_membership`）只能退出**本人**的成员行；他人成员资格由既有空间治理流程处置。`role='space_admin'` 退出返回 409 `SPACE_MANAGER_TRANSFER_REQUIRED`（必须先交接），前端不得绕过。`GET /spaces` 的 `my_member_id` 提供当前账号在该空间的成员行 id。退出是终态 `removed`，无「撤销退出」。

### 权限授予判定（服务端实时计算，无缓存）
> **[v2 取代]** 以下 QU1=B「直系边完整互见」规则已被 §0.1 四级可见性取代：直系结构边跨空间最多 lineage_summary，不再自动 full。

**QU1 已裁定为修订版 U5（2026-08-25，用户确认；v2 已取代）**：

完整数据访问 ⇔ **双方在同一空间且均为 active 成员 ∨ 两端点之间存在至少一条 dir_class ∈ {elder, younger, spouse} 的 active 关系边**。

- 直系结构边（亲子/配偶）是信任代理：对端互见完整档案——家谱核心语义是血缘链上的信息可见。
- peer 边对端与仅 clan 连通可达者 → 摘要（名字/称谓/世代）；其余 invisible；搜索遵循同一基线。
- pending 期间：发起方可看接收方摘要（通知需要），反之亦然。断连/移出即时降级。
### 成员关系词标注 `member_relation_labels`（09-20）

加入空间时填写的「我和对方是什么关系」（兄弟、朋友、闺蜜等自由文本，≤64），是
**显示层标注，不是亲属事实**：

- 表结构：`(space_id, user_a_id, user_b_id)` 唯一（端点规范化为 `user_a_id < user_b_id`），
  一对人一条；`CHECK(user_a_id != user_b_id)`、`CHECK(length(label) BETWEEN 1 AND 64)`。
- **绝不进入** `source_facts` / `relations` / `social_relations`；**不参与**关系路径推导、
  可达性、世代计算或 `topology_edges`。填「朋友」不会让两人产生任何亲属联系，也不扩大
  任何可见范围。
- 渲染：`PersonalFamilyViewOut.label_edges`（读取时按当次授权节点集合过滤，两端都在集合内
  才返回；不进 steward 快照，故不参与投影版本失效链）。家族树按第三种边样式（点线 + 斜体标签）
  叠层绘制，不参与布局。
- 授权：`PUT /spaces/{space_id}/member-relation-label`，**仅该对两端本人**可改，改完即时生效，
  无需对方确认、无需房主审批；空串 = 清除（移除标注边）。
- 退出/被踢后该端点不再在授权集合内，标注边立即不再返回。
