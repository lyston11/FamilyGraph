# 父任务决策记录与讨论笔记

## 1. 需求纠偏

初始设计把 system_admin 作为同一 SPA 中的第二种主体：家庭和后台共用端口、router、bundle、localStorage 和公开 API，只靠 JWT `principal_type` 与路由守卫隔离。实际走查发现，家庭用户访问 `/system-admin/login` 会被静默送回家庭空间，且家庭 bundle/API 可以发现后台代码。这满足了一部分后端权限安全，却不满足“用户端完全不知道系统管理员存在”以及“独立后台”的产品目标。

因此本父任务不再沿用 09-01 任务的单 SPA 结论，而是把后台提升为独立平台边界。

## 2. 已确认决策

- 家庭前台和系统后台使用不同前端项目、不同端口、不同 origin、不同存储和不同构建产物。
- 家庭 API 8000 与 Admin API 8002 使用独立 listener；8002 由同容器独立 FastAPI app 提供，生产不发布到宿主。
- 家庭端产品与公网隐藏：不承诺有机器访问权的技术人员无法扫描端口，但家庭 bundle、家庭路由、家庭 API 和公开文档不泄露后台。
- 后台以“空间管理员 → 其管理空间”为监控主线，不把后台做成任意表的数据库浏览器。
- 系统管理员主体与家庭用户的 `space_admin` 关系完全不同；空间管理员不是全局管理员。
- 后台业务范围是全业务只读但排除认证秘密、私人正文和高敏感档案；关系只读结构化已确认事实，Agent 错误为服务端原文保留、API 二次脱敏。
- 普通列表/运营元数据直接读取并审计；敏感详情需要绑定单个 user 或 space、有效 30 分钟的访问会话和理由。
- 首版除空间管理员申请审批外不做写操作；approve 不强制理由，reject 必须理由，均二次确认和审计。
- 系统管理员使用用户名 + 强密码。单一账号初始为 `admin`，随机密码写入 0600 文件，首次改密后删除；不接受固定 admin/admin，不做旧 PIN 迁移，MFA 后续再做。
- 家庭端未来的注册另立任务；本任务不新增电话、邮箱、地址等 User 字段。

## 3. 重要取舍

### 3.1 为什么不是只改端口

只把同一个 SPA 从 5173 复制到 5174 仍会把后台路由、组件、API 路径和身份字符串编译进家庭 bundle，也不能隔离 localStorage 或公开 API。因此必须从项目入口、模块图、API listener、JWT 签发域到部署网络一并拆分。

### 3.2 为什么不直接注册旧 admin.py

旧 `admin.py` 把家庭 PIN 重置、档案修改、数据权利、争议决议和其他 break-glass 混在平台运营路由里。直接挂载会绕过新的只读字段合同和审计票据，也会重新开放家庭数据高风险写权限。新后台只实现显式 read model 和唯一审批写例外。

### 3.3 为什么使用独立访问审计表

现有 `audit_log.actor_id` 关联家庭 `users`，不能可靠表达独立 system_admin。把管理员 id 塞进 `detail_json` 会导致查询和约束不可执行。因此新增直接引用 system_admin 的访问会话/审计表，永久保留但不保存响应正文。

## 4. 冲突决策的最终解释

讨论早期曾出现“后台首启页”和“所有 bootstrap 只在 8002”的方案；随后用户确认“系统管理员默认存在”，最终以部署自动 bootstrap 为准：默认账号由受控启动流程生成，不向家庭端提供初始化页面，也不把公开初始化能力作为后台产品功能。必要的部署状态检查只能在 admin listener/运维通道提供。

## 5. 不可静默改变的边界

- 不得把 `is_admin`、`owner_id`、其他空间角色或家庭 visibility 当作 system_admin 授权。
- 不得把家庭用户 token 当作后台 token，也不得只靠前端隐藏。
- 不得返回 PIN/密码哈希、JWT/refresh token、secret、prompt、消息、上下文、工具结果、关系证据原文或附件原文。
- 不得在当前模型没有字段时伪造电话/邮箱/地址功能。
- 不得覆盖并行工作树修改；实现前后都必须复核 bundle、路由和网络矩阵。
