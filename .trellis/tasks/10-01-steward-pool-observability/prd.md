# 池尖峰不可观测：缺产品内诊断

## 目标

让「长 run 期间连接池被谁占住、事件循环是否被阻塞」在**产品内**可直接观测，
不再依赖外部探针 + `py-spy` 事后拼接。据此定位池尖峰的持有者并决定收敛方案。

限定开发环境；线上由用户手动发布。

## 背景（已确证的既有缺陷链）

三个独立缺陷已修或已定位：

1. **事件循环被同步 SQL 阻塞**（已修 `ade03e4`）：provider 流每 chunk 在事件循环上
   调 `_refresh_run_gate`；池满时阻塞 30s/chunk。
2. **run token 10 分钟硬过期**（已修 `b656d89`）：心跳复用租约时的 token，
   >600s 的 run 必得 401。
3. **池尖峰致心跳被拖过期**（**未修，本任务目标**）：run 252 心跳空档 157s 后收到
   409。实测稳态 6 并发 worker 池峰值仅 6/15、心跳最差 5ms——**不饱和**，
   因此是尖峰而非稳态；持有者与时长尚未测出。

## 事实与证据边界

- 已有证据：`research/evidence/`（前序任务）记录 30s/chunk 事件循环阻塞、
  401 token 过期、157s 心跳空档 → 409。
- 池占用只能从进程外近似（数 `/proc/<pid>/fd` 里的 `app.db` 句柄，实测 21 个）。
- **未测出**池尖峰时刻的持有者、持有阶段与时长。这正是本任务要补的。
- 事件循环延迟目前完全不可观测（无 `loop lag` 指标）。
- 产品内没有任何 pool/loop 诊断，排查依赖外部脚本 + `py-spy` + journalctl 拼接。

## 需求

### R0 产品内可观测性（前置）

必须在产品内提供诊断，且**不依赖被占满的执行队列**（诊断本身要能在池满时仍记录）：

- **连接池等待**：记录每次 checkout 的等待时长与当时占用（checked out / size /
  overflow）。等待超阈值时输出结构化告警。
- **事件循环延迟**：周期性测量事件循环被阻塞的时长，超阈值告警。
- **阶段归属**：能区分「连接池等待」「事件循环阻塞」「SQL 执行」——不得把总响应
  时间笼统命名为「线程池耗尽」（上一任务已因此误判两次）。

### R1 据此定位池尖峰持有者

用 R0 的诊断，在真实负载下测出：

- 池尖峰时刻的连接持有者（哪个阶段/哪个调用方）；
- 单次持有的时长分布；
- 触发条件（何种并发组合使需求超过 15）。

**未测出持有者之前不得实施收敛方案**——上一任务已证明「凭推断施工」会修错地方。

### R2 收敛方案（取决于 R1）

根据 R1 证据选择：缩短持有时间 / 为 steward 分离池 / 限制并发叠加。
**不得**用「调大池上限」掩盖：SQLite 单写者下增大池只增加锁竞争。

### R3 合同不变

- 不改 wire 协议、不新增端点、不改 schema、不改 fence/幂等/审计语义。
- 诊断日志字段仅含安全标识（路由模板、run id、时长、计数），
  不得含正文、token、凭据、SQL 参数（`logging-guidelines.md` 红线）。
- 诊断不得成为新的全局锁或串行点。

## 验收

| ID | 可观察结果 |
|---|---|
| AC-0 | 池等待与事件循环延迟在产品内可观测；超阈值有结构化告警，字段无敏感数据 |
| AC-1 | 用该诊断在真实负载下指出池尖峰的持有者与持有阶段（非推断） |
| AC-2 | 诊断本身在池满时仍能记录（不依赖被占满的队列） |
| AC-3 | 据 AC-1 证据实施收敛（若证据支持），心跳不再被拖至租约过期 |
| AC-4 | backend 全量 pytest / ruff / mypy 通过；agent 未改则说明 |
| AC-5 | 既有 Provider/fence/结算合同回归通过 |

## 不在范围

- 调大连接池上限或放宽 `pool_timeout` / 任何租约或超时。
- 重构 provider 转发架构或拆独立服务。
- 回填历史 `expired` run。
- 线上操作。


## 执行结果（2026-10-01）

### 已交付

- 两个独立信号：`db_pool_wait`（池等待 + 占用）、`event_loop_lag`（事件循环延迟）。
- 顺带修复既有缺陷：`JsonFormatter` 丢弃所有 `extra=`，导致诊断与 `counters` 无值。

### 诊断的直接结论：**证伪了池尖峰假设**

`db_pool_wait` 部署至今 **0 次**——池从未接近耗尽。因此上一任务记录的
「连接池需求超过上限」**不是**这些停滞的原因。部署后 1 小时：0 次 >20s 停滞、0 expired。

### AC-1 未完成

已排除池，但停滞（历史 96–195s、run 262/288 的 409）的真实机制**仍未定位**。
`event_loop_lag` 触发 4 次但量级小（阈值 500ms），与历史长停滞不匹配；
历史停滞发生在诊断部署前，缺少同期数值。

**不得据此宣称已解决**。后续需要：在诊断覆盖下等待一次真实复现，或回到栈采样
（`py-spy`）在停滞发生时抓现场。
