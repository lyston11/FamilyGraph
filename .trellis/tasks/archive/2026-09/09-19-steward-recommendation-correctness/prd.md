# PRD：管家错误推荐修复

## 目标

消除管家把已确认亲子、祖孙推荐为兄弟姐妹，以及双方已共享家庭空间仍推荐共建家庭的情况。修复应贯穿生成、读取、通知、用户操作和存量收敛，不通过换模型、隐藏文案或清空数据掩盖问题。

## 授权与状态

- 2026-09-19 用户明确要求“为上述问题创建 trellis 任务并写清楚修复方法和具体的执行步骤”。
- 当前仅获准创建任务及规划；保持 `planning`，未批准实施、生产数据处理或部署。
- 本任务采用一个串行修复包：两条错误推荐共用 Steward 交付、通知及验收链，不拆成并行修改相同模块的任务。A 为关系线索，B 为共同家庭判定，C 为两者存量收敛和统一验收。
- 修复设计及执行步骤分别见 [design.md](design.md)、[implement.md](implement.md)。

## 问题与证据边界

- 用户截图：`/Users/lyston/.cache/clipaste/shot-mu81c26s.png`、`/Users/lyston/.cache/clipaste/shot-mu81k4md.png`。前者展示子女被当成兄弟姐妹线索，后者展示朱元璋与马皇后的共建家庭卡。
- 代码已核对：候选结构校验与同类型事实去重不能拦截亲子/祖孙被标为 `direct_sibling`；`_pair_inputs` 只在当前空间为 household 时计算共同成员资格，lineage 中恒为 false。
- 前次口头诊断的存量统计互相矛盾，不作为验收基线：不能认定全部 26 条 sibling 建议都错，也不能把 21 张待处理 household 卡等同于 21 张无效卡或 21 个空间。正式处理前必须以可复跑规则逐条重验。
- `space_profile_refs` 无记录本身不证明数据或代码缺陷；本任务不更改建档选择及 no-space 合同。
- 详见 [核对摘要](research/diagnosis-summary.md)。本轮没有重新读取生产库，不声称最新线上数量或状态已复核。

## 需求

- R1：`direct_sibling` 模型线索遇到当前获权 confirmed 亲子事实或生物祖先/后代路径时，不得生成公开关系建议、通知或推测边；两个方向等价处理。具体保守判定范围见设计，不引入“任意不同关系均互斥”的假设。
- R2：历史错误线索即使证据 hash 没变，也不得继续作为有效待核实条目或推测树边；旧详情、旧链接、提交及推测转正不能绕过实时重验。
- R3：保留 `legacy/unsupported` 中不与已确认事实冲突的线索；缺少正向支撑不等于矛盾。共同父母证书仍仅内部核验，不伪造证书，不把 `unsupported` 一律改成 `versioned`。
- R4：双方在任一 household 空间均为 active 成员时，不再推荐通过 ActionCard 创建共同家庭；是否扫描自 lineage 空间不影响判定。仅共同 lineage、profile ref、pending/退出成员均不足以判定已有共同家庭。
- R5：共同家庭已满足只取消 `create_household` 动作，不误取消仍合法的 `request_lineage`。不禁止用户通过现有自主创建流程建立其他家庭，不自动加入或合并空间。
- R6：新卡生成、旧卡读取/通知、后台复核、accept/execute 必须采用一致的共同家庭判定；读到旧卡后才获得共同成员资格的竞态也不能再通过该卡创建重复家庭。
- R7：后台持久收敛复用既有 job/delivery/FSM，在正常周期或显式重跑中完成；不等待卡片 TTL，不要求再次模型调用或证据 hash 变化。
- R8：保留候选及证据历史、用户私人忽略/共享驳回、已提交提案和已确认事实、通知已读状态及既有冷却。不删行、不伪造 `resolved`/`executed`、不自动撤销用户确认。
- R9：亲属事实仍限当前空间及允许的全局事实，个人响应继续受 VisibilityPolicy 约束。跨空间共同家庭检查仅为既定两端点的内部布尔抑制信号，不提供他空间名称、ID、成员列表、内部关系或发现能力。
- R10：部署和数据收敛的结果须与代码/隔离测试分开报告；生产处理前在线备份、dry-run 清单、隔离演练及用户授权缺一不可。

## 非目标

不更换 Provider/模型，不扩大 prompt 中私人资料；不重构关系引擎或称谓呈现，不扩充共同父母证书，不清空通知/候选表，不修复未证明的 profile-ref 问题，不修改已确认关系，不实现延期的跨空间亲属发现，不改变自主建空间规则。

## 验收标准

| ID | 可验证结果 |
| --- | --- |
| AC1 | fake 模型输出亲子/祖孙 sibling（含反向）时，建议、recipient、notification 和推测边增量均为零；同批合法候选仍可正常处理 |
| AC2 | 历史错误建议及推测边在 list/detail/notifications/overlay 中不再呈现为可行动线索；GET 零写；submit/confirm/reinstate 在事务内拒绝，无新 SourceFact 或确认副作用 |
| AC3 | 无冲突 unsupported 仍按既有流程处理；共同 biological_parent 支撑的 versioned 双向内部隔离与不可变历史继续通过回归 |
| AC4 | lineage 中扫描配偶，双方已在另一个 household active 时无 household_link；无共同 household 时仍正常出卡；合法 lineage_request 保留 |
| AC5 | profile ref、pending/rejected/退出成员、只有共同 lineage 均不误抑制；无权请求保持原 403/404，响应及日志不泄漏其他空间信息 |
| AC6 | 旧卡 pending/viewed/accepted 经复核成为 superseded；已终态卡不改写。旧页面 accept/execute 重验失败且不新增家庭；并发交付/操作、复核重跑幂等 |
| AC7 | 证据未变也能收敛历史错误记录；另一 household 中增删成员后，读取和命令立即使用当前状态，健康扫描在约定队列处理窗口内持久收敛；无无界跨空间广播 |
| AC8 | 重验前后受保护历史逐字段相同；已提交/已确认异常只列为人工核查，不被自动撤回。处理报告按对象 ID、类别、判据区分总量与命中量 |
| AC9 | 定向回归、完整后端静态检查/测试及隔离浏览器验收通过；若执行发布，另记录实际服务版本/schema/配置与用户可见结果，不以 health 200 替代 |

## 规划审阅门

设计明确提出对旧“仅本 household 成员”判据的修订：允许只返回共同成员资格布尔值的抑制查询，不开放他空间内容。批准实施前需审阅这一有限边界修订；用户批准最新规划后才运行 `task.py start`。生产部署及存量写操作仍须单独明确授权。
