# F 验收缺口补齐：取消端到端计时与撤权浏览器语义

## 状态与目标

planning。父任务 `09-17-dual-agent-latency-result-integrity`。前置：`09-17-dual-agent-controlled-acceptance` 已归档（41/41 + 19/19 通过）。

目标：补齐 F 自报未覆盖的必需格，并把两处「结论说得比证据满」的表述收敛到证据能支撑的范围。本任务只补缺格与修正口径，**不重跑已通过场景，不部署，不调用真实模型**。

## 背景：为什么已归档的 F 仍不够

F 的 `evidence/matrix.md` 末尾明确写着「失权的浏览器可见语义：UI 组没做……属另一轮环境搭建」。而 F-R4/AC4 的原文要求覆盖「断线 Last-Event-ID 恢复、刷新、取消、**失权**、跨空间切换」。因此「41/41 + 19/19 全过」只证明**已执行的格**全过，不等于需求全量覆盖。

同时有两处表述超出证据：

1. **`converged_after_s=0.01` 不是端到端取消耗时。** `run_controlled_acceptance.py` 的顺序是「发取消 → `collect_worker()` 等待 worker 退出 → 才开始计时 → 查询终态」。该值度量的是「worker 已退出后再查到终态」的延迟，不能证明用户点击取消后 10ms 结束。生产维护循环默认 `MAINTENANCE_INTERVAL_SECONDS=5`，且每 tick 还含其他维护工作，故当前只能确认「不再必须等租约过期（原 304s）」。
2. **`compaction` 口径需要写准。** D2 把压缩改为 run 级 `run.compacted` 是对的（真实 SDK 两次压缩都在 turn 之外），但必须写清：prompt 前那次归 `prepare`、`agent_start` 之后那次才单列、`model_turn` 仍可能含上游重试与等待（不得称纯推理）、`settle` 仍是持久事件间隔估计而非精确结算 CPU 耗时。

## 需求与验收

| ID | 需求 | 验收结果 |
| --- | --- | --- |
| G-R1/AC1 | 取消计时可归因 | 探针分别记录并报告三个独立量：**取消接受时间**（点击/请求 → 取消 API 返回）、**终态可见时间**（取消 → 观察到终态）、**执行停止时间**（取消 → worker 进程/在途连接结束）。三者分别有值与来源说明；不得再用「等 worker 退出后才开始计时」的量冒充端到端取消延迟。 |
| G-R2/AC2 | 取消与真实失败的竞态有明确结论 | 新增回归：取消已请求后，若 sidecar 结算 `failed`（真实失败，非取消），终态与事件必须如实为 `failed` 且不被改写为 `cancelled`；反向，取消后 sidecar 结算 `succeeded` 仍改判 `cancelled`。断言谁先提交、最终状态、审计行，以及后续 reaper 不覆盖已落终态。 |
| G-R3/AC3 | 撤权的真实浏览器语义 | 真实浏览器 + 真实 sidecar + 真实 API：另一账号经正常授权路径撤销正在接收流的账号成员资格后，断言 ① 旧流停止、② 受限内容按合同清理、③ 重连/刷新/迟到事件不能复活旧内容、④ worker 不继续工具调用且旧执行者零业务写回。 |
| G-R4/AC4 | 口径修正与证据可复现 | `matrix.md` 与相关 spec 的压缩/取消表述改为证据支撑范围；新增补验记录**追加**而非覆盖原归档结果；两个脚本仍是零真实模型费用、自动分配端口、退出即清理。 |
| G-R5/AC5 | 不越界 | 不修改生产默认参数（尤其不通过调小 `MAINTENANCE_INTERVAL_SECONDS` 让探针变好看）；不重跑全部已通过场景；发现产品缺陷退回所属任务。 |

## 非目标

- 不实施「取消请求事务内直接终态裁决」——G-R1 只要求先把端到端耗时测准；若测出默认配置下终态等待仍显著影响体验，另立任务专项处理取消与成功/失败结算的竞态。
- 不做 G（发布与真实小样本）与 I（档位/并发取舍）的工作。
- 不新增测试框架；沿现有两个 smoke 脚本与既有测试目录。
- 不改 09-18 已冻结的增量显示协议、有界性与安全结论。
