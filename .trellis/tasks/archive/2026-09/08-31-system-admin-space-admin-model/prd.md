# PRD：系统管理员与空间唯一管理员模型重构

## Goal

把 FamilyGraph 的权限模型恢复为产品原始设计：**系统管理员是独立的平台后台身份；管理员资格绑定具体家族/家庭空间；每个正常空间恰好只有一个属于本空间的管理员；一个用户可以同时成为多个不同空间的管理员。**

用户价值：家庭成员可以分别维护自己所属的家族脉系，同时在婚姻/家庭关系形成的共同家庭空间中共存；系统管理员只能维护平台治理所需的账号、成员关系和空间元数据，不能浏览家庭档案内容。

## Background and confirmed product contract

以下规则由用户确认（2026-08-31），是本任务的固定要求：

1. **系统管理员 / 运维员**是独立的系统管理身份，不是家庭成员。
   - 没有自己的用户档案、家族、家庭空间或空间成员关系。
   - 登录后进入独立的系统管理员后台，不进入家庭空间应用壳。
   - 只查看和管理账号、成员关系和空间元数据，以及平台治理所需的管理员归属/申请信息。
   - 不查看家庭档案内容、家族关系图中的家庭数据、私人资料或其他敏感内容。
2. **管理员身份绑定具体空间，而不是绑定用户全局。**
   - 每一个正常家族空间只有一个且必须有一个该空间的管理员。
   - 家庭空间同样只有一个且必须有一个该空间的管理员；创建、迁移和交接事务之外，不允许提交零个或两个本空间管理员。
   - 同一个用户可以管理多个不同的空间；因此不能用全局 `user.is_admin` 表示空间管理员。
3. 一个家庭空间的成员列表中可以出现多个“管理员”用户，但这些人分别管理其他空间，并不因此获得当前家庭空间的管理权限。
   - 例如：父亲是当前家庭空间的管理员；母亲是其母系家族空间的管理员。母亲在当前家庭空间中仍是普通成员，除非她另有当前空间的管理员关系。
4. 用户可以为自己所属的那一脉家族申请成为对应 `lineage` 家族空间的管理员，向系统管理员申请并由系统管理员审批；这不是申请当前家庭空间的全局管理员身份。申请卡片必须明确显示目标家族空间名称；若目标 `lineage` 已有管理员，系统管理员必须先向原管理员发送可追踪的工单/站内通知，原管理员明确同意后才可以完成管理员交接。
5. 产品和权限模型只保留一个“空间管理员”角色；`owner` 与 `space_admin` 不是两个并列角色。
   - 现有 `owner`、`owner_id` 和 owner 移交只是历史实现/兼容数据；迁移后不能作为第二种管理员或第二套授权来源，也不能产生一个空间拥有两个本空间管理员。

## Requirements

### R1. 身份与账号边界

- 系统管理员账号与家庭用户/PersonProfile 解耦；系统管理员不得创建或占用家庭档案、家族、家庭空间和 `SpaceMember` 关系。
- 首次初始化创建的是系统管理员凭据，并只返回一次初始 PIN；初始化完成后系统管理员可以登录独立后台。
- 平台身份必须由服务端权威身份/角色判断，不能由客户端字段或全局 `is_admin` 兼容投影决定。
- 家庭用户的账号、档案和空间成员关系继续保持现有认证与生命周期安全约束。

### R2. 空间管理员唯一性

- 每个正常 `family_space` 必须恰好一个 active 的本空间管理员；创建、迁移和管理员交接只能在同一事务内短暂经过中间状态，不能提交零个或两个管理员。
- 一个用户可以在多个不同 `family_space` 中分别拥有管理员资格。
- “本空间管理员”必须按 `(user_id, space_id)` 判定；不得使用 `is_admin(user_id)` 判定空间治理权限。
- 当前家庭空间中的其他用户即使是别的空间管理员，也只能按其在当前空间的实际角色获得权限。
- 管理员显示应明确其管理归属空间，避免把“某空间的管理员”误显示为“当前空间管理员”。

### R3. 那一脉家族空间管理员申请与审批

- 申请目标必须是一个明确的、已存在的 `lineage` 家族空间；申请记录必须包含申请人、目标空间、申请状态、提交/裁决时间和系统管理员裁决信息。
- 用户可以为自己所属的那一脉家族申请管理员；实现层要求申请人已是目标 `lineage` 空间的 active 普通成员并完成身份确认，尚未加入目标空间的用户先走成员加入流程；不能把该申请泛化为当前 `household` 的管理员申请。
- 用户侧申请卡片必须显示目标空间名称和空间类型，使用明确文案，例如“申请成为「母系家族」家族空间的管理员”；提交确认和申请状态中都必须保留该目标名称。目标名称由服务端根据 `space_id` 返回，不能信任客户端自带名称。
- guest、非成员和非 active 成员不能提交；目标空间已有管理员时仍可提交，但必须进入原管理员同意工单流程；同一申请人对同一目标空间最多一条 pending 申请。
- 系统管理员只能在独立后台查看最小审批信息：申请人账号标识、目标空间元数据、当前管理员账号标识、当前成员关系/角色元数据、申请状态和申请理由（若存在）；不得返回档案详情或家庭关系内容。
- 系统管理员审核通过进入交接准备后，必须向目标空间当前 active `space_admin` 发送可追踪的管理员交接工单/站内通知。通知至少包含申请人账号标识、目标空间名称和交接说明，不包含家庭档案内容。
- 原管理员只能在自己仍是目标空间 active `space_admin` 时处理该工单；明确同意后才允许管理员交接。原管理员拒绝时申请终止为 rejected，当前管理员保持不变；系统管理员不能绕过拒绝直接交换。
- 原管理员同意后，系统管理员才可执行最终 approve；最终 approve 必须在同一事务中把申请人从 active `member` 升为唯一 `space_admin`，把原管理员降为普通 `member`，并同步必要的兼容字段。事务提交后不得出现零个或两个本空间管理员。
- 如果系统管理员审核或交接期间目标空间、申请人或原管理员资格发生变化，工单失效并停止交换；申请保持 pending 或进入明确终态，必须重新核验，不能使用过期同意。
- 若目标空间因迁移/修复暂时没有管理员，只能走独立的、可审计的空间修复或创建流程；正常管理员申请不通过制造“无管理员空间”来绕过上述同意条件。
- `household` 的初始管理员由空间创建/既有管理员交接流程确定，本任务不把家庭空间改造成另一套管理员申请模型；无论建立方式如何，提交后的家庭空间都必须恰好一个本空间管理员。
- 审批拒绝、原管理员拒绝、工单发送/处理、重复裁决、失效申请和并发交接必须记录理由并保持状态机一致性与审计完整性。

### R4. 家庭用户侧权限与界面

- 家庭用户在当前空间看到的“管理员”仅表示当前空间的本空间管理员。
- 用户在其他空间的管理员身份可以在账号/空间关系元数据中展示，但不能改变其在当前空间的权限。
- 对外只显示“空间管理员”；不得继续用“空间所有者”和“空间管理员”表达两个产品层管理员等级，`owner` 也不得作为独立权限来源。
- 空间管理入口、成员治理、空间改名和邀请等能力必须根据当前目标空间的管理员关系进行授权；系统管理员不因平台身份自动获得这些能力。
- 用户申请入口不得使用无目标的“申请成为管理员”卡片。入口必须列出可申请的目标 `lineage` 空间，每张卡片明确显示空间名称，并在提交、待审批和已裁决状态中保持目标空间上下文。
- 原管理员收到的工单/通知必须明确显示“申请人正在申请成为「目标空间名称」的空间管理员”，并提供同意/拒绝动作；同意前不得改变任何管理员关系。
- 系统管理员不显示家庭空间导航、家庭成员导航、统计、记忆/知识和家庭搜索入口。

### R5. 独立系统管理员后台

- 系统管理员后台使用独立的布局/导航/路由入口，不复用家庭用户的 `AppShell` 作为登录后的默认壳。
- 系统管理员登录后默认进入系统管理员后台；访问家庭应用路由应被拒绝或导向后台首页，不得展示家庭数据页面。
- 后台至少提供以下元数据视图：
  1. 系统账号列表与账号生命周期状态；
  2. 管理员账号与其管理空间的归属关系；
  3. 空间列表及空间类型、创建/状态、管理员账号等空间元数据；
  4. 成员关系和角色状态元数据；
  5. 那一脉家族空间管理员申请、原管理员交接工单与裁决记录。
- 后台接口只能返回上述最小元数据；管理员申请审批、交接工单和管理员关系变更所需的写操作，也只能改变申请/工单/管理员关系元数据。禁止返回或编辑家庭档案字段、关系图详情、附件内容、私人会话/记忆和高敏感披露字段。
- Provider、Agent、系统策略等其他平台运维能力不属于本任务；既有接口如继续存在，必须保持各自既有安全边界，不得借本任务扩大系统管理员的家庭数据范围。
- 后端 API 必须独立做平台角色授权和最小字段投影，不能只依赖前端隐藏菜单。

### R6. 数据、迁移与兼容

- 所有角色、唯一性和归属约束必须落在服务端和数据库层；不能只在前端维护。
- 需要提供 Alembic 迁移，处理现有 `owner`、`space_admin`、`family_spaces.owner_id`、`platform_role_assignments`、管理员申请和管理员交接工单数据的兼容关系；迁移后只保留一个规范的空间管理员角色和一个本空间管理员授权来源。
- 迁移不得静默删除空间、成员或管理员关系；发现无法自动收敛为唯一管理员的冲突数据时必须失败并给出可诊断错误，或通过显式、可审计的修复步骤处理。
- 现有 `platform_operator` 命名可以作为内部兼容迁移标识，但产品和 API 契约必须明确其为独立系统管理员身份；不能继续让其表现为家庭用户。
- 现有 `is_admin`、owner/space_admin 双角色、owner 移交流程和管理员申请流程的兼容字段/接口需要在设计中明确保留期、替代接口和移除条件。

### R7. 审计与隐私

- 系统管理员登录、管理员申请提交/审核、交接工单发送/查看/同意/拒绝、管理员关系变化、账号治理操作都必须写入审计日志。
- 审计内容只包含治理所需元数据；PIN、JWT、密钥、家庭档案详情和私人数据不得写入日志或响应。
- 系统管理员的元数据查询必须可审计；查询接口不得成为家庭数据的旁路读取入口。

## Acceptance Criteria

### 角色与数据边界

- [ ] 首次初始化后，系统管理员可以登录并直接进入独立系统管理员后台。
- [ ] 系统管理员在数据库中没有家庭用户档案、空间成员关系、家庭空间或家族资料归属；服务端禁止通过普通家庭端点访问家庭数据。
- [ ] 系统管理员后台及接口只返回账号、成员关系和空间元数据；自动化测试证明家庭档案、关系图详情、附件、私人会话/记忆和敏感字段不会出现在响应中。
- [ ] 普通家庭用户登录后仍能进入家庭应用；平台身份不能让其获得系统后台权限。

### 空间管理员模型

- [ ] 任一正常空间恰好存在一个 active 的本空间管理员；迁移、创建和交接完成后不能留下零管理员或双管理员。
- [ ] 同一用户可以在空间 A 和空间 B 分别成为管理员；在空间 A 中其权限只由空间 A 的关系决定。
- [ ] “父亲是当前家庭空间管理员、母亲是她所属母系家族空间管理员”的场景可通过 API 和前端展示正确表达：母亲在当前家庭空间仍是普通成员，不能管理当前家庭空间。
- [ ] 管理员申请卡片明确显示目标 `lineage` 空间名称；用户不会在多个家族空间之间因泛化“申请成为管理员”文案而产生歧义。
- [ ] 对外只显示“空间管理员”；不会再出现 `owner` 与 `space_admin` 两个产品层管理员等级，`owner` 不再作为独立权限来源。
- [ ] 管理员交接、那一脉家族空间申请审批和成员移除等并发/状态转换不会产生双管理员或无管理员的已提交状态。

### 申请与后台治理

- [ ] 普通家庭用户只能为明确目标 `lineage` 家族空间提交管理员申请；不能通过该申请成为当前 `household` 的管理员；非成员、pending、guest 不能提交。目标空间已有管理员时允许提交，但必须经过原管理员同意，不能直接交换。
- [ ] 系统管理员审核申请后必须向目标空间原管理员发送可追踪工单/通知；原管理员拒绝时当前管理员保持不变，原管理员同意前不能发生角色交换。
- [ ] 原管理员同意后，系统管理员可以在同一事务内完成唯一管理员交接并记录理由；重复裁决、过期同意和并发裁决安全失败。
- [ ] 管理员归属、成员角色变化和裁决均产生可查询审计记录。

### 回归门禁

- [ ] 后端：`.venv/bin/python -m pytest -q`、`.venv/bin/python -m mypy app`、`.venv/bin/ruff check .`、`.venv/bin/ruff format --check .` 全部通过。
- [ ] 前端：`npm run type-check`、`npm run lint`、`npm test`、`npm run build` 全部通过。
- [ ] 关键流程包含 API 授权/防 IDOR 测试、数据库迁移空库/现有数据冲突测试、前端路由壳和元数据字段投影测试。

## Out of scope

- 不改变家庭关系图的业务语义、可见性策略、RAG/Agent 内容授权或家庭档案字段模型，除非为阻断系统管理员越权所必需。
- 不实现系统管理员查看家庭档案的 break-glass 能力；如未来需要，必须另立审计强化任务。
- 不增加多级系统管理员、权限组、组织租户或批量运营工作流。
- 不改变普通家庭成员邀请的既有“邀请后由受邀人接受”语义。
- 不在本任务中设计新的家庭空间创建产品流程；只确保创建后恰好存在一个本空间管理员，并处理管理员归属、那一脉家族空间申请和既有交接流程的一致性。
- 不保留“系统管理员同时作为家庭用户”的兼容行为作为长期产品能力；如迁移期必须兼容，必须隔离并标记为临时迁移路径。
- 不在本任务中新增 Provider、Agent、系统策略等平台运维范围；系统管理员的可见数据边界固定为账号、成员关系和空间元数据，以及申请/交接工单所必需的最小记录。
- 不在本任务中规定外部短信、邮件或推送渠道；管理员同意工单至少以可审计的站内通知/待办实现，外部通知渠道可另立任务。

## Open questions

- 无产品阻塞问题。实现必须遵循固定结果：每个正常空间恰好一个本空间管理员；管理员按空间绑定且可跨空间复用；普通申请只针对申请人所属的 `lineage` 家族空间；系统管理员独立且只接触账号、成员关系和空间元数据；`owner` 不再是第二种管理员。
