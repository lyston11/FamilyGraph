# 纠正：根因是 Tailscale DERP 丢路由，不是 PII 正则

## 结论（推翻本任务 PRD 的前提，也推翻我当时的归因）

`transport_timeout` 100% 失败的根因是 **Tailscale DERP 中继丢失到上游 peer 的路由**，
**不是**进程内状态损坏，**也不是**我声称的 PII 正则超线性回溯。

```
magicsock: derp-7 does not know about peer [B31ZQ], removing route
          ↑ 每 ~5 秒重复，贯穿整个故障期
```

`B31ZQ` = `lyston的MacBook Air` = `100.71.18.78` = provider 2 的上游主机。

## 决定性证据：DERP 丢路由次数与 egress 失败数**逐小时吻合**

| 时段 | DERP 丢路由/小时 | egress 失败/小时 |
|---|---|---|
| 10-01 09–23 | ~189–211 | ~95 |
| **10-02 07–10** | **0** | **0** |
| 10-02 11 | 119 | 59 |
| 10-03 01–12 | ~282–292 | ~144 |
| **10-03 13** | **26** | **0** |

10-03 全天计数 **3490**，10-01 故障小时 211——与失败量同步涨落。

## 时间吻合

| 事件 | 时刻 |
|---|---|
| 最后成功 egress | 10-01 08:57:11 |
| DERP 首次丢路由 | 10-01 08:57:32（**21 秒后**） |
| 首个失败 egress | 10-01 09:02:17 |

## 自愈（进程从未重启）

`NRestarts=0`，进程启动于 10-02 16:14，但故障在 **10-03 13:00 自愈**。
**进程内状态不会自己恢复**，因此「进程内状态损坏」被否证。
10-02 03:00、06:00 也各有部分/完全恢复，同样没有重启。

## 纠正我的两处错误

### 错误 1：把 PII 正则当作根因

实测复核旧正则：

```
旧正则 len=17,837（真实 payload）:  2,781ms
旧正则 len=66,000（合成大 payload）: 38,103ms
```

真实 payload 是 **2.78 秒，不是 23 秒**（我当时用合成的大 payload 外推到真实场景）。
更根本的是：`before_provider_request` 在 HTTP 请求**构造之前**执行，
httpx 的 connect 超时尚未开始计时——策略耗时**不可能**产生 `ConnectTimeout(sent=False)`。

### 错误 2：把「恢复」归功于 PII 修复

恢复发生在 **10-02 06:00**，PII 修复 **16:14** 才部署。
更直接的否证：PII 修复部署后，**10-03 00:00 故障完整复发**（0/144 成功）。

## PII 正则仍是真实缺陷（性质不同）

它在真实 payload 上就要 2.78 秒且超线性（4x 输入 → 15.7x 时间）。py-spy 抓到
`contains_pii` 在**事件循环线程**上，与 3275ms 的 health 延迟吻合。
它是**真实的秒级事件循环停顿**，值得修（已修：66KB 23.4s → 1.9ms），
但**不是**出站 100% 失败的原因。

## 本轮故障的真实性质

上游 provider 是用户的 MacBook，经 Tailscale DERP 中继（`relay "sin"`，
**无直连**：`direct connection not established`）。DERP 在该时段不认识该 peer，
移除路由后所有到 `100.71.18.78:8443` 的连接都失败。服务端无法修复中继本身。

## 应用侧可改进点

1. **重试风暴放大**：失败 run 每次产生 **24 条 egress** = 请求层 6 次
   （`providerStreamMaxRetries=5`）× 会话层 4 次（`SESSION_RETRY_BUDGET.maxRetries=3`）。
   一次 10 秒的不可达被放大成约 240 秒无效工作，并制造 144 条/小时审计噪声。
   成功 run 只用 1–5 条。
2. **失败分类不区分「上游不可达」与「上游拒绝」**：两者都落 `transport_timeout`，
   使运维无法从审计看出是中继问题。
