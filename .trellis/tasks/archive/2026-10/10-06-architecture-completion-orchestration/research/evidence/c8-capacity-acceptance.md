# C8：多租户容量验收（可执行部分）

## 覆盖范围（严格界定）

本探针覆盖**当前已实现**的三层配额，在真实 PostgreSQL 上并发验证：

| 层 | 配置 | 观测 | 判定 |
|---|---|---|---|
| 租户级（space） | 每租户 2 | `{1: 2, 2: 2, 3: 2}` | 无越限 |
| 集群级（cluster） | 全局 3 | 占用 3 | 无越限 |
| 流级（global/kind/tenant） | global 4 / kind 3 / tenant 1 | 占用 3，每租户 1 | 无越限 |
| 归还守恒 | — | 归还后非零计数行 **0** | 无泄漏 |

```
PASS: 租户/集群/流三层配额守恒，归还不泄漏
```

## 变异验证（暴露了兜底机制，这本身是有价值的发现）

**只删应用层容量检查** → 探针**仍然通过**。原因不是探针没判别力，而是
`CHECK (active <= capacity)` 在数据库侧拦住了超额并回滚了事务。

**同时删掉应用检查 + 弱化 CHECK** → 探针立刻失败：

```
占用 12 每租户 {1: 4, 2: 4, 3: 4} 越限 [1, 2, 3]
占用 12（期望 ≤ 3）
FAIL:
  - 租户级越限：[1, 2, 3]
  - 集群级越限：12 > 3
  - 流级 tenant 越限：[1, 2, 3]
  - 流级 kind 越限：12 > 3
```

因此**两层都是承重的**：应用层负责「跳过满租户看下一个」的正常路径，CHECK 负责
「应用层漏检时也无法超额」的兜底。这个结论只有通过**双重变异**才能得出——
单层变异会让人误以为检查没生效。

## 明确未覆盖（不得据此宣布系统达标）

| 未覆盖 | 归属 |
|---|---|
| 真实 p95/p99 延迟 | 需要真实负载与多实例部署 |
| 真实 DERP/provider 故障 | `10-04-provider-reliability-boundaries` |
| 真实 sidecar 多实例 | `10-04-control-plane-fault-domain` AC-5 |
| 真实用户可见结果 | 需要开发环境灰度（C9） |
| PgBouncer / 连接预算实际形态 | `10-04-postgres-operations-cutover` |

**把这些混在一起会让「探针通过」被误读成「系统达标」**，因此探针在 PASS 时也会
打印未覆盖清单。

## 证据等级

**L3（原型）**：真实 PostgreSQL 多连接、真实并发竞争、真实三层配额、含双重变异。
**不是**真实多实例部署或真实负载验收。
