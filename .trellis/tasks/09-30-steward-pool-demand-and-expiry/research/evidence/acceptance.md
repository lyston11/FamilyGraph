# 验收证据（2026-09-30）

## 两个独立缺陷，均已定位

### 缺陷 1：run token 10 分钟硬过期（已修）

`AGENT_RUN_TOKEN_TTL_SECONDS_MAX` = 600s，而 token **只在租约时签发一次**。
心跳复用同一 token，因此任何存活超过 600s 的 run 必然在心跳时收到 **401**，
sidecar 把 401 当作租约失效（`worker.ts` 的 `[401,403,409,410]`）并 abort。

两个独立样本吻合：

| run | 租约时刻 | token 过期 | 401 出现 | 偏差 |
|---|---|---|---|---|
| 232 | 12:56:09 | 13:06:09 | 13:06:17 | +8s |
| 244 | 14:55:38 | 15:05:38 | 15:05:56 | +18s |

**修复**：心跳响应回传续签的 token（`HeartbeatOut.run_token`），sidecar 采用它。
续签只复制**已校验过的** token claims，不扩大权限；字段 additive，旧客户端忽略。

**验证**：部署后 **401 心跳 0 次**（修复前每个长 run 必有一次）。
负向验证两侧：去掉服务端续签 → 后端用例失败；client 丢弃 token → sidecar 用例失败。

### 缺陷 2：连接池需求超过上限（未修，已定位）

修复 token 后仍有 1 个 `expired`（run 252，存活 501s < 600s），机制不同：

```
16:31:31  心跳 200（正常）
16:31:31 ─┬─ 心跳空档 157s
16:34:08 ─┘ 心跳 409（服务端已判失租）
16:34:08  sidecar: lease lost, aborting run 252
```

**409 不是 token 问题**（token 已续签），而是**心跳请求本身被拖住 157 秒**，
租约在此期间自然到期。这与上一任务测到的池耗尽一致：steward 的 4 个 core 线程 +
每空间 2 个 assist + 心跳/lease 轮询共同争抢 15 条连接；实测慢响应时
**4 个线程在等连接、仅 2 个在执行**。

事件循环阻塞已修（慢响应时 MainThread 停在 `select`），因此这是**工作线程在池里排队**，
不是全进程静默——表现为个别请求（含心跳）变慢，严重时租约过期。

| 变异 | 结果 |
