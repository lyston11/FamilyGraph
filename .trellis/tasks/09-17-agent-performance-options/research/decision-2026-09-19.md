## 2. 零费用排队/吞吐实测（I-R4/AC4）

`scripts/smoke/run_performance_options_probe.py`（隔离 DATA_DIR + 脚本化上游，零费用）。
轮询保持出厂的 250ms，不调小以美化 `queue_wait`。

| 运行 | 提交 run | 注入生成 | `queue_wait`（s） | 总时长（s） | 被拒 |
| --- | --- | --- | --- | --- | --- |
| A | 2 | 300ms | 0.889 / **2.280** | 1.843 / 3.226 | 0 |
| B | 2 | 600ms | 0.840 / **3.319** | 2.895 / 5.332 | 0 |
| C | 2 | 1200ms | 0.456 / **4.694** | 4.263 / 8.503 | 0 |
| D | 4 | 300ms | 0.476 / 1.848 | 1.425 / 2.804 | **2** |
| 重复 1/2/3 | 3 | 900ms | 0.909→4.185 / 0.463→3.693 / 0.454→3.673 | — | 1 |

### 四条可复现事实

1. **单 worker 确实是串行的**：第二个 run 的 `queue_wait` 恒为正且随第一个的生成时长增长
   （注入 300ms→2.28s；1200ms→4.69s）。等待已用源计时归因，不是持久间隔推断。
2. **账户并发上限是 2**（实测事实，非文档推断）：提交 4 个 run 时，后 2 个被
   `409 AGENT_RUN_LIMIT`（`detail.reason=AGENT_RUN_ACCOUNT_LIMIT`）拒绝。
   **这是「加 worker 并发」能否提速的关键前提**：只加 sidecar worker 数而不动
   账户上限，第 3 个 run 仍会在入队阶段被拒——并发度被业务约束钉住，不在 worker 侧。
3. **未观察到 SQLite 锁竞争**：并发提交 4 次耗时 34–43ms，无 `database is locked`。
   但这是**空库 + 无并发写负载**下的结果，不能外推到有 Steward 重算并行的生产负载。
4. **排队占比可量化**：run 2 的 `queue_wait` 约占总时长的 **55–71%**
   （注入 300ms 时 70.7%；600ms 时 62.3%；1200ms 时 55.2%；900ms 三次重复 55–60%）。
   注意这是**受控注入**下的比值——真实生成时长是 11.47s 量级
   （09-18 统计中位数），排队占比会更低。

### 证据边界

- 注入的生成时长是**常量**，不是模型速度；本探针证明的是**机制**（串行、排队来源、
  上限位置），不是真实收益。
- 本机同机测量，不报告跨机精度。
- 不证明扩并发后的真实吞吐改善：需要知道真实到达率与单次生成时长分布。

## 6. 结论

- 本项目**不需要**降档或换模型来满足任何未闭合的验收：AC-06 允许在主要瓶颈位于上游时
  交付可信归因与可审阅方案，本文件即该方案。
- 排队是**真实存在且有界**的，但**账户并发上限**而非 worker 数才是扩容的硬约束；
  在不知道真实到达率之前不主张扩容。
- 三个目标（首段更早 / 完整更快 / 吞吐更高）分别有不同证据状态，本文件不混报。
