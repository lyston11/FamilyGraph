# 修复 Memory 未启用时缺少可操作入口

## Goal

让 Memory 和 RAG 的“未启用”状态成为一条可完成、可解释的产品路径：用户不再进入一个始终可见但只能收到 503 的记忆页面；具备权限的运维人员能够在管理端找到并管理两个平台级开关，普通家庭用户能够知道下一步该做什么。

## Background / Confirmed Facts

- 截图中的家庭端 `/memory` 页面无条件显示在应用壳次级导航中，页面加载时会同时请求候选、私有记忆和当前空间记忆。
- `backend/app/config.py:216-217` 的 `MEMORY_ENABLED`、`RAG_ENABLED` 只读取环境变量，默认关闭；当前没有家庭端或系统管理员端的 Memory/RAG 开关接口。
- `backend/app/api/memory.py:62,107` 以及 `backend/app/services/memory_rag.py:49-56` 在关闭时分别返回 Memory/RAG disabled 错误。
- `frontend/src/components/memory/MemoryManager.vue` 把加载错误显示为黄色告警，但仍继续渲染待确认、私有记忆、共享记忆、检索与引用等操作入口；`frontend/src/components/shell/AppShell.vue:261-266` 也始终暴露“记忆与知识”导航。
- 现有系统管理员域已有独立认证和后台路由；`backend/app/api/admin_steward.py` 已提供“即使功能关闭也可读取状态”的运维状态模式，但 Memory/RAG 没有对应的状态/配置合同。
- `MEMORY_ENABLED` 和 `RAG_ENABLED` 均为平台级开关，不属于当前家庭空间的成员权限或个人偏好；两者需要保持相互独立、分别可读写和回滚。
- 现有 `agent_platform_defaults`、受控联网平台配置及 Steward 平台辅助开关治理任务提供了平台单例配置、审计和管理端入口的可复用模式；本任务应先核对其最终落地状态，避免重复造配置机制。
- 本任务只处理两个平台级开关的产品可用性和入口闭环，不改变 Memory/RAG 的隐私隔离、候选确认、scope、索引或授权规则。

## Product Requirements

### MR-1 未启用状态必须可解释且可完成

当 Memory 或 RAG 未启用时，家庭端不得只显示裸的 503 错误。页面必须明确说明对应能力当前未启用，这不是用户数据丢失或操作失败，并提供符合最终权限模型的下一步指引。

### MR-2 两个开关必须有明确的管理入口

平台级 Memory 和 RAG 开关必须在与其权限边界一致的独立系统管理员管理端可发现、可读取当前状态并执行启用/停用；启用和停用均需有明确反馈。不能要求管理员只能通过未记录在产品界面的 shell 环境变量完成操作。

### MR-3 前后端状态合同一致

家庭端应消费后端提供的 Memory/RAG 能力状态，而不是猜测环境变量或把任意 503 都当成“未启用”。能力未启用、部署/维护异常和网络失败应能区分，并保持服务端为最终真源。

### MR-4 关闭时避免误导性操作

对应能力未启用时，家庭端不得继续呈现会必然失败的操作作为可用功能：Memory 关闭时不应提供新增、确认、忽略、撤销、删除等写操作；RAG 关闭时不应提供检索或引用保存入口。页面可保留产品说明或受控预览态，但不能让用户以为操作已经可用。

### MR-5 保持权限和数据边界

只有独立系统管理员主体能够修改平台级开关；家庭用户、普通空间成员、空间管理员不得通过家庭端接口改变开关。系统管理员端只读写开关元数据，不因此获得家庭记忆、候选、RAG 文本或其他家庭领域内容读取权。

### MR-6 两个开关独立且可回滚

Memory 与 RAG 必须独立启停。停用任一能力不得意外改变另一能力、Assistant、Steward、结构化领域工具或既有数据的持久化和授权语义；重新启用后既有数据仍按原合同处理。

### MR-7 保留部署级安全兜底

产品化平台开关不能削弱部署级 kill switch 和 fail-closed 行为。若实现保留环境变量作为初始值或紧急关闭通道，必须明确其与数据库平台开关的优先级，并在管理端展示“部署级关闭”与“平台级关闭”的区别，避免管理员误以为界面启用已经生效。

## Acceptance Criteria

- [x] AC-1：Memory/RAG 关闭时，家庭端显示对应的明确未启用状态和下一步指引，不显示对应的误导性可执行操作；刷新/返回等安全动作仍可用。
- [x] AC-2：具备平台开关权限的系统管理员能在独立管理端看到 Memory、RAG 当前状态并分别启用、停用；操作结果在刷新后仍与服务端状态一致。
- [x] AC-3：普通家庭用户和空间管理员无法通过家庭端或伪造请求修改任一平台级开关；未授权请求 fail closed。
- [x] AC-4：Memory/RAG 开启时，现有候选、记忆、共享记忆和检索功能行为不回归；既有服务端真源重载与错误处理仍成立。
- [x] AC-5：前端能区分“对应能力未启用”与至少一种真实服务异常（如网络/部署失败），并分别呈现可行动文案。
- [x] AC-6：开关组合全部可解释：Memory/RAG 均关、仅 Memory 开、仅 RAG 开、两者均开时，家庭端状态与 API 行为符合各自合同，不互相误报。
- [x] AC-7：平台开关修改经过系统管理员权限校验并写入现有审计机制；响应不包含家庭内容或秘密。
- [x] AC-8：新增或调整的后端权限、状态合同、家庭端和管理端行为均有针对性自动化回归测试。

## Out of Scope

- 不改变 MemoryCandidate、Memory、RAGDocument/RAGChunk 的数据模型、授权过滤、确认流程、索引策略或隐私策略。
- 不把 Memory/RAG 开关下放为普通用户或空间管理员可以修改的个人/空间设置。
- 不新增自动保存聊天、隐式索引或绕过候选确认的直接发布流程。
- 不把环境变量、部署脚本或其他现有未提交业务改动做无关重构。

## Key Decision

已确认：**Memory 和 RAG 都是平台级开关，且彼此独立。** 管理入口采用独立系统管理员后台；家庭端只负责消费状态并在关闭时显示可行动说明，不向家庭用户暴露平台开关写入口。

## Blocking Questions

无产品阻塞问题。数据库配置与环境变量的优先级、数据模型是否复用既有平台配置表等属于技术设计阶段需要基于现有实现核对的事项，不改变上述产品行为。
