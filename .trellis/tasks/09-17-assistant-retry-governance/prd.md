# E：助手网关错误分类与分层重试治理

## 状态与目标

planning；本轮仅创建规划，未授权改策略或真实调用。父任务 `09-17-dual-agent-latency-result-integrity`，主会话内联。目标：错误可安全分类、每次真实出站可审计、Provider 与 session 两层重试总量可解释且有界。

## 基线与问题

`main@d8d3668`：`backend/app/services/provider_proxy.py:302` 部分 HTTPError 路径缺 egress 审计，`:309` 将所有上游 >=400 统一转502。Pi Provider 层把408/409/429/5xx视为可重试，因此上游认证/参数永久错误可能被重复发送。`agent/src/session.ts` 保留默认 session retry；所用 SDK 默认启用、最多3次，另有配置的 Provider 请求重试5次。是否叠加及真实出站数须逐场景验证，不能机械声称所有 run 都请求24次。

## 需求

| ID | 要求 |
| --- | --- |
| E-R1 | 保持错误体脱敏、家庭/internal 权限隔离，同时区分不可重试、暂时可重试、取消/失租和结果未知；认证/参数错误不得伪装为可重试上游5xx。 |
| E-R2 | 每次实际网关出站尝试有唯一、完整的安全审计终态，包括连接异常、响应头失败、流中断、取消、成功；发送前拒绝单列，不冒充上游请求。 |
| E-R3 | 明确请求层与会话层重试责任、有限次数、时间/取消边界及 Retry-After 处理；压缩恢复与普通网络重试分开。 |
| E-R4 | 保持 Provider/模型/档位、授权与现有预算；不得自动换端点、云回退、降低推理，或放开管家 unknown 重发。 |
| E-R5 | 对需改变总次数/等待上限的方案给出实际调用数、费用和可用性取舍，取得独立选择后才实施；工程分类与观测修复不以此冒领策略授权。 |

## 验收

| ID | 可观察结果 |
| --- | --- |
| E-AC1 | 本地上游400/401/403不会进入普通5xx重试循环；408/409/429/5xx依批准策略处理，sidecar 不能读到上游私密错误体。 |
| E-AC2 | 两层重试经过真实 SDK+本地假上游，实际请求数与审计数逐条对账；一次失败成功、耗尽、stream断开、压缩后恢复均有可解释序列。 |
| E-AC3 | 连接失败/取消/失租也留安全终态，重复清理不双记；取消后不再发生新请求，活动连接有界关闭。 |
| E-AC4 | 重试期间不绕过 membership、run active、cloud consent、工具allowlist；真实未知处理保持保守。 |
| E-AC5 | D 指标能消费完整审计；旧审计缺失仍标未知，不补写历史虚假失败数。 |
| E-AC6 | 策略表、SDK锁定版本、次数/预算推导、剩余待决策项写入证据；未批准的策略不部署。 |

## 依赖与非目标

D 后执行：请求 ID/attempt/turn 与 retry layer 的形状由 D 冻结，E 负责可靠生产。与 D/F、所有 Provider 与 SQLite 工作串行。F 累计复验，G 发布。

不升级 SDK、不新增通用重试框架、不实现熔断平台或人工重发入口。本任务可先完成错误分类与审计修复；若总重试策略未决，必须保留 E-R3/E-R5 未完成，不能以部分实现归档全任务。推荐先保留既有合法暂时错误的有限配置，仅修永久错误误重试；任何进一步降低重试预算需数据支持。
