# 助手低延迟响应与首段交付优化

## 状态与授权

父任务：`09-17-dual-agent-latency-result-integrity`。2026-09-18 用户要求“模型请求的响应速度一定不能慢”，反馈每次问助手都要十多秒才回答，随后批准“创建子任务并继续”。当前为 in_progress：P0-1 轮询优化已实现并部署；P0-2 增量显示已实现（sidecar/后端/前端 + 回归测试均通过），待部署与真实浏览器验收。不视为新协议冻结、模型降档、生产发布或真实付费探针的批准。主会话内联，无子智能体。

## 目标

实质降低用户提交问题到可读回答的等待，分别验收首段正文和完整答案；不得用加载提示、快速失败或降低答案质量冒充提速。不能只重复父任务的归因报告便宣布本任务优化完成。

## 已确认背景

本次源码基线 `main@5c2f0a5`，未重新核查运行服务。

- `agent/src/events.ts:209–257`：只在 `message_end` 发布完整正文，忽略 `message_update`；用户当前并非边生成边看。
- `agent/src/worker.ts:77–90`、`agent/src/config.ts:106–110`：单 worker 串行，每次循环后都等待轮询间隔，默认 2000ms（包含完成任务之后）；事件批量提交默认 250ms。它们不是十多秒等待的完整解释，部署值尚未核查。
- E 的永久 4xx 修复已集成；正常首发成功不会经历失败退避。两层预算仍冻结为请求层 5 + 会话层 3，改变次数必须沿 E-R5 审批。
- E 的约 79s 来自快速失败假网关，不是线上最坏墙钟上限；先前答复把候选退避时间写成“最坏墙钟”不准确。请求耗时、工具轮次、压缩和 Retry-After 必须另计。
- 旧的两条真实 run 不能代替用户当前链路，完整生成、重试、排队和渲染仍需同 run 的实测。

完整来源与限制见 [研究摘要](research/latency-summary.md)。

## 体验目标（2026-09-18 用户确认）

**普通短问答：提交后 3 秒内出现有信息量的安全正文，8 秒内完整回答。** 长回答可持续输出；工具/复杂推理独立列出首正文与完成时间，不一刀切 3 秒中断。

该目标是验收口径，不是已测承诺；达标与否必须用同配置前后对照判定。

测量不能把“我来看看”、thinking、工具状态、空白、报错当首段答案。真实 Provider 无法保证任何负载下每次必达；超标必须保留原值、原因和失败率，不隐藏长尾。

## 与既有任务分工

本任务负责用户体验目标、优先级和提速交付，并自 2026-09-18 起承接增量显示协议与安全合同（原 H 任务已归档，其约束折入本任务 design）。E 管重试策略；I 管模型/档位/并发取舍；F 管受控矩阵与浏览器验收；G 管发布与真实验证。采用某方案时，在对应任务记录决定及唯一代码归属，串行实施，再把证据链接回本任务。

**2026-09-18 调查结论**:主因是流式可见性链路中断(SDK delta 被显式丢弃)+ 请求层重试放大上游不稳定;次级因素包括排队轮询、per-chunk DB 事务、cache key 不稳定。详见 `research/pi-vs-familygraph-latency.md`。

**2026-09-18 实施记录（P0-2 增量显示）**:协议与安全合同已落地，实际字段为 `assistant.text_delta` / `assistant.text_reset`（无 message key；身份是 run×turn），有界性已冻结（2000/4000 码点）。已核实的限制：**当前没有输出侧正文扫描**，因此增量与完整消息面对同一（缺失的）检查，实现按合同采用“明示未覆盖”分支而非声称等价。回归：agent 160 / backend 1703 / frontend 762 全通过。**LL-AC4 仍未完成**：需真实浏览器证明「完整答案前看到安全正文、最终文本一致、重连不重、不串主体」，以及实际部署（backend 必须先于 sidecar，否则新事件类型会让整批 append 422）。

## 非目标

不重构 Agent 框架、不添加独立重试平台或监控平台、不自动降低回答质量、不删历史、不篡改历史审计，不把总超时缩短当推理提速。当前不进行生产迁移、重启、配置修改或真实模型请求。

## 已完成的只读生产核查（2026-09-18，含当晚更正）

线上两次真实 run：排队 0.94s / 11.05s；工具执行约 1ms；结算与正文相差约 11ms；平台未显式设置推理档位，SDK 回退 `medium`；正文只在整条消息结束时公开，SDK 增量被 `agent/src/events.ts` 显式丢弃。

**更正**：首轮读表把「单轮 33.15s / 53.04s」当作模型生成耗时，**这是错的**。用 `agent_provider_egress` 审计按 run 对账后，同一轮内多次物理请求与退避可测：

| 轮次 | 失败请求 | 退避 | 成功请求 | 轮总时长 |
| --- | --- | --- | --- | --- |
| run 1 turn 1 | **29.77s**（1×503） | ~0.4s | ~19.4s | 53.04s |
| run 1 turn 2 | **29.92s**（1×503） | ~0.4s | ~9.2s | 39.63s |
| run 2 turn 1 | 无 | — | 4.30s | 4.30s |
| run 2 turn 2 | ~4.5s（5×502） | **~11.6–15.5s（含末次退避）** | 14.1–16.1s | 33.15s |

相邻间隔 1.658/1.620/2.695/4.247s 只与**请求层**退避 `min(0.5·2^i,8)s` 吻合；会话层退避是 2/4/8/16s，全部大于观测间隔，可直接排除。成功请求本身为 3.9–19.0s（不含失败与退避），因此不能据此断言模型一定够快。

**由此确定的主导项是「上游不稳定 × 重试策略」**，两种形态：

- **慢失败**（run 1）：单次 503 自己就耗时 29.8s 才返回；退避无关紧要，需要「首字节/失败期限」。
- **快失败 + 用满退避**（run 2）：5×502 本身约 4.5s，但请求层退避总量（含成功前最后一次）约 **11.6–15.5s**。

另更正：**不存在「15s 请求超时」这条因果链**。`AGENT_REQUEST_TIMEOUT_MS=15s` 只作用于 sidecar→FastAPI 的 internal 调用；模型流经 pi-ai 且未设 `timeoutMs`（SDK 默认 10 分钟），网关是 300s 总超时 / 10s 连接超时。先前把「15s 超时 + 2s 退避 + 16s」当作 33s 的解释同样错误。

完整数据见 [实测证据](research/latency-evidence-2026-09-18.md)。**以上全部为未部署状态的只读观测**；远端运行 `8ae6414`，不含本任务的任何修改。
