# 助手低延迟研究摘要

## 当前结论

用户反馈每次提问等待十多秒；源码能证明存在多段潜在等待，但尚不能把十多秒归因到单一根因。当前应将“首段可见”和“完整答案”分开测量。

## 已确认事实

- sidecar `agent/src/worker.ts` 单实例一次执行一个 run；空闲轮询默认 `AGENT_LEASE_POLL_MS=2000`，事件批量 flush 默认 250ms。两者是可消除的程序性等待候选，不等于真实线上配置。
- `agent/src/events.ts` 只把 assistant `message_end` 转成公共正文事件，`message_update`/delta 不公开；即便 SDK 已有正文，浏览器也可能要等完整消息结束。
- 前端 `frontend/src/stores/agent.ts` 发送后才开启 SSE，`frontend/src/components/agent/MessageList.vue` 只有获得非空 assistant 正文才结束等待指示；当前 10 秒排队/30 秒运行提示不是性能优化。
- E 已将永久上游 4xx 改为真实 4xx + no-retry，避免错误重试；正常首发成功仍可能被模型本身、工具、压缩或网络拖慢。
- 当前会话层重试预算显式为 3 次、请求层配置默认最多 5 次；E 的假网关永久失败实验得到 24 次物理请求、约 79 秒整轮，但这是失败样本，不是正常响应的硬上限，也不能直接作为生产费用。
- Pi 自动压缩必须保留，不能用 recent-N 截断或关闭压缩制造低延迟。
- 已有 `assistant_phases` 和 sidecar timing 能覆盖 queue/prepare/model turn/tool/compaction/provider retry 的部分服务端阶段；浏览器 SSE 首帧/渲染仍需受控浏览器证据。

## 根因假设排序

1. 正常首发生成/首 token慢（需要真实 Provider/模型测量）；
2. 完整消息发布边界导致“已经生成但页面不可见”（需要 SDK→网关→SSE→浏览器测量）；
3. sidecar 空闲轮询造成入队到 lease 的最多约 2 秒（需核对实际配置及队列样本）；
4. 工具轮次、上下文准备或自动压缩占用主要时间（需要 source timing）；
5. 瞬态网络重试造成尾部延迟（由 E 审计与 F 受控矩阵验证）；
6. SQLite/单 worker 排队（需多 run 本地零费用受控实验，不默认扩容）。

## 当前不应得出的结论

- 不把历史两条 run 当作当前 p95；
- 不把 `created_at`、心跳或 `message_end` 单独当作首字时间；
- 不认为减少重试能加速一次成功请求；
- 不认为增量显示能减少模型推理时间；
- 不认为代码合入 main 等于远端服务已加载；
- 不以快速错误、thinking、工具状态或空消息作为首段答案。

## 待用户确认

推荐把产品性能目标拆成：健康、短、无工具请求在提交后 3 秒内出现安全的有信息量首段，8 秒内完整回答；复杂工具/长上下文只保证尽快首段并单独报告完整时长。该目标是候选，不是已测承诺。确认后再冻结实施验收和是否需要 H 的安全增量协议。
